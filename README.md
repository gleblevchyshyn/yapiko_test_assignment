# AI-парсер замовлень Yapiko

Сервіс перетворює довільне повідомлення клієнта («две филадельфии и том ям, Науки 47») на структуроване замовлення з позиціями з меню. Все, що не вдалося однозначно зрозуміти, позначається для уточнення оператором, а не вигадується.

```
POST /parse  {"message": "...", "now": "2026-10-26T14:00:00+02:00"}
→ items / ambiguous / unavailable / not_found / delivery / payment / persons / total_uah / needs_clarification
```

---

## Як запустити

### Docker (основний спосіб)

```bash
cp .env.example .env        # вписати LLM_API_KEY (і за потреби LLM_BASE_URL / LLM_MODEL)
docker compose up --build
```

Сервіс: `http://localhost:8000`, Swagger UI: `http://localhost:8000/docs`, healthcheck: `GET /health`.

```bash
curl -s -X POST http://localhost:8000/parse \
  -H "Content-Type: application/json" \
  -d '{"message": "здравствуйте, пиццу 4 мяса с сырным бортом и колу"}'
```

Підключення до вашого LiteLLM-проксі — лише через `.env`, без змін коду:

```bash
LLM_BASE_URL=http://litellm:4000/v1
LLM_API_KEY=...
LLM_MODEL=<назва моделі в LiteLLM>
```

### Локально (для розробки)

```bash
uv sync
uv run uvicorn yapiko_test_assignment.main:app --reload
```

Без обов'язкових змінних сервіс не стартує і показує, чого саме не вистачає (fail fast).

### Eval

```bash
# сервіс уже запущено
uv run python eval.py --label my-model

# порівняння кількох моделей: eval сам піднімає сервіс для кожної моделі з eval_models.json
uv run python eval.py --models eval_models.json --concurrency 2

# лише окремі приклади
uv run python eval.py --ids dev_04,dev_09
```

Результати друкуються і зберігаються в `eval_results/<label>.json` (метрики + кожен приклад із розбіжностями).

## Архітектура

```
POST /parse
   │
   ▼
LLM (розуміння тексту)          →  LLMOutput: згадки страв + доставка/оплата/персони
   │                                 (факти з тексту, без рішень)
   ▼
rules.py (детерміновані правила) →  ParseResponse
   - SKU є в меню?             → інакше not_found
   - 2+ кандидати?             → ambiguous
   - у стоп-листі?             → unavailable
   - опції: валідація + default
   - total_uah, графік 11–22, needs_clarification
```

Головний принцип: **LLM повертає факти, код ухвалює рішення.** LLM не бачить цін і стоп-листа і не вирішує, що потрапить у замовлення.

### Структура

```
src/yapiko_test_assignment/
  main.py      FastAPI app, lifespan: меню, стоп-лист, prompt і LLM-клієнт створюються один раз
  api.py       POST /parse, GET /health; тонкий шар: llm_call → build_response
  config.py    налаштування з env (pydantic-settings)
  schemas.py   контракт API, модель меню, схема відповіді LLM
  menu.py      завантаження menu.csv / stop_list.json
  prompts.py   system prompt + рендер меню
  llm.py       виклик моделі через instructor
  rules.py     бізнес-правила (pure functions, без мережі)
eval.py        оцінка якості на dev_set
```

### Ключові рішення

**Що робить LLM, а що код**

| LLM | Код |
|---|---|
| які страви згадав клієнт, скільки, опції, коментарі | чи існує SKU, розкладка по `items / ambiguous / unavailable / not_found` |
| кандидати SKU для кожної згадки | стоп-лист, борт за замовчуванням, валідація опцій |
| адреса, час, тип доставки, оплата, кількість персон | `total_uah`, графік 11:00–22:00, `needs_clarification` |

**Гарантія «немає вигаданих SKU» забезпечується кодом**, а не моделлю: кандидати від LLM фільтруються по меню, усе, чого там немає, відкидається. Тому навіть найслабша модель в eval має 0 вигаданих SKU.

**Схема відповіді LLM — список кандидатів, а не одне `sku` + прапорець `is_ambiguous`.** Неоднозначність обчислюється з даних (`len(candidates) > 1`), тож протиріччя між полями неможливе. Якщо один із двох кандидатів вигаданий, другий валідний лишається і позиція коректно потрапляє в `items`.

**Схема LLM окрема від контракту API.** `LLMOutput` має описи полів (вони йдуть у JSON Schema, яку бачить модель) і змінюється під час роботи над prompt. Контракт API (`ParseResponse`) фіксований завданням. Між ними стоїть `rules.py`.

**Поля, яких може не бути в тексті, nullable.** Обов'язкове поле без `None` змушує модель вигадати значення (наприклад, кількість персон).

**Переносима схема.** Тільки прості типи, enum, nullable і списки об'єктів із фіксованими полями, без відкритих словників. Перша версія з `options: dict[str, str]` падала на Gemini у режимі tool calling (`MALFORMED_FUNCTION_CALL`); після переходу на `list[OptionChoice]` і режим `json` схема працює на всіх протестованих моделях.

**Structured output — через [instructor](https://python.useinstructor.com/).** Pydantic-модель як `response_model`, повтор із текстом помилки валідації, і головне — `mode` налаштовується через env. Різні моделі за LiteLLM підтримують різні механізми (tool calling, `response_format`), тож режим підбирається без зміни коду.

**Prompt**
- Статична частина (інструкції + меню) іде першою, текст клієнта — окремим `user`-повідомленням. Це дає кешування префікса у провайдерів (Gemini, OpenAI — автоматично).
- Меню рендериться з тих самих даних, що використовує `rules.py`, тож prompt і перевірки не можуть розійтися.
- У меню для моделі **немає цін і надбавок**: модель не може їх «порахувати» чи змінити на прохання клієнта.
- Стоп-лист не передається моделі: вона має розпізнати страву, а «немає в наявності» вирішує код. До того ж prompt лишається стабільним, і кеш працює.
- Текст клієнта загорнутий у `<customer_message>`, prompt прямо каже, що це дані, а не інструкції.
- Few-shot прикладів немає, щоб не підганяти систему під dev set. Під час розробки я перевіряв, щоб у prompt і описах полів не потрапили фрази з dev set.
- `temperature=0`: для витягування даних потрібна детермінованість.

**Стоп-лист перечитується при зміні файлу** (за `mtime`), меню завантажується один раз. Стоп-лист міняється протягом дня, і перезапуск заради нього неприйнятний. У Docker `data/` змонтовано як volume.

**Fallback на оператора.** Якщо LLM недоступна (таймаут, 429, вичерпані повтори), сервіс повертає порожнє замовлення з `needs_clarification=true` і заголовком `X-LLM-Fallback: true`, а помилку пише в лог із traceback. Заказ не губиться, а збій видно в метриках. Помилки в `rules.py` навмисно **не** перехоплюються: це баг у коді, і він має бути помітним (500).

**Токени і вартість — у заголовках відповіді** (`X-Prompt-Tokens`, `X-Completion-Tokens`, `X-Cost-USD`, якщо провайдер його віддає), щоб не змінювати JSON-контракт.

### Трактування, яких немає в ТЗ

- **22:00 входить у графік** (11:00 ≤ час ≤ 22:00).
- **Неоднозначність визначається до стоп-листа**: кандидати зі стоп-листа лишаються в `ambiguous` (як у dev_04).
- **Один валідний кандидат після фільтрації = однозначний вибір**, відкинуті SKU вважаються галюцинацією моделі.
- **Борт за замовчуванням = варіант із надбавкою 0** (виводиться з меню, а не захардкоджено). Якщо такого варіанту немає (як у «Добавка» в SP04), опція не додається.
- **Опція або значення, яких немає в страви, відкидаються**, лишається значення за замовчуванням.
- **Однакові позиції не об'єднуються**: дві піци з різними бортами — два рядки. Сума від цього не залежить.
- **`now` приймається в контракті, але поки не використовується**: у ТЗ явно вимагається лише перевірка графіка, а «час уже минув» — це вже моє трактування (див. «Що покращив би»).

## Вибір моделі

Порівняння на dev set (20 прикладів), однакові prompt і код, різниться лише `LLM_MODEL`:

| Модель | Повністю вірні | Items F1 | `needs_clarification` | Небезпечні авто-OK | Latency avg | $ / 1000 запитів |
|---|---|---|---|---|---|---|
| llama-3.1-8b | 5/20 | 90% | 65% | **1** | 2.9 с | $0.91 |
| **qwen3-30b-a3b** | **17/20** | 100% | 95% | 0 | 4.4 с | **$0.45** |
| gemini-2.5-flash-lite¹ | 11/20 | 93% | 75% | 0 | 1.5 с | $0.49 |
| **gemini-2.5-flash** | 15/20 | 98% | 95% | 0 | **1.1 с** | $1.64 |
| qwen3-235b-a22b | 15/20 | 100% | 100% | 0 | 11.8 с | $0.49 |
| gemini-3.5-flash | 16/20 | 100% | 100% | 0 | 5.5 с | $13.88 |

Вигаданих SKU — **0 у всіх моделей**.

¹ 4 з 20 запитів отримали 429 від спільного пулу Google в OpenRouter (зовнішній rate limit, не якість моделі), результат ненадійний.

**Рекомендація: `qwen3-30b-a3b`.** Найкраща якість на dev set, нуль небезпечних помилок, найдешевша. Це open-weight MoE-модель (~3B активних параметрів), її реально підняти на власному залізі через vLLM за вашим LiteLLM. Latency тут — це latency провайдерів OpenRouter, на власному GPU вона буде іншою.

**Альтернатива через API: `gemini-2.5-flash`.** Найшвидша і найстабільніша (p90 1.4 с) за близької якості.

Не рекомендую:
- `gemini-3.5-flash` — reasoning-модель: ~820 completion-токенів на запит проти ~135 в інших. Через це в 8 разів дорожча і в 5 разів повільніша за gemini-2.5-flash без помітного виграшу в якості.
- `qwen3-235b` — якість на рівні, але 12–22 с на відповідь неприйнятні для клієнта в чаті.
- `llama-3.1-8b` — єдина з небезпечною помилкою (підставила страву, якої клієнт не замовляв, і пропустила замовлення без оператора).

**Застереження:** 20 прикладів — це мало, 1 приклад = 5 п.п. Різниця 17 vs 15 — не доказ переваги, а сигнал, що моделі співставні.

## Результати eval

### Як рахуються метрики

- **Позиції** порівнюються за сумарною кількістю на SKU: два рядки по одній піці = один рядок на дві. Precision / recall рахуються в штуках.
- **Опції та коментарі** — окрема метрика для збіглих SKU, щоб бачити, де саме помилка.
- **Адреси і тексти** порівнюються після нормалізації (регістр, пунктуація, пробіли). `not_found` збігається, якщо один текст містить інший.
- **`ambiguous`** порівнюється за набором кандидатів і кількістю, а не за текстом.
- **Вигадані SKU** — усі SKU у відповіді (items, кандидати, unavailable), яких немає в меню.
- **Небезпечні авто-підтвердження** — очікувалось уточнення, а сервіс сказав «можна без оператора». Це найдорожча помилка для бізнесу, тому вона рахується окремо від загальної accuracy `needs_clarification`.
- **Fallback і HTTP-помилки рахуються як провал**, а не пропускаються. Під час аналізу знайшов баг: fallback-відповідь збігалася з очікуваним «порожнім замовленням» і зараховувалась як успіх. Виправлено.

Окремо перевірено `rules.py`: якщо подати на вхід «ідеальну» відповідь LLM, зібрану з еталону, всі 20 прикладів відтворюються повністю. Отже, всі помилки нижче — це помилки розуміння тексту моделлю, а не правил.

### Розбір помилок

| Помилка | У кого | Наслідок |
|---|---|---|
| Адреса у відмінку клієнта: «Сумську», «Пушкінської», «с Героев Труда» | усі Gemini, qwen-235b, llama | кур'єр зрозуміє, але для геокодування гірше |
| «том ям» → ambiguous між супом SP04 і піцою P10 | усі Gemini, qwen-235b | безпечно: замовлення йде на уточнення. Еталон вважає це однозначно супом, але трактування спірне |
| Зайві кандидати іншого типу: сет S11 для «филадельфии», яєчна локшина W05 для «удону» | Gemini, qwen-235b, llama | безпечно, але зайве уточнення оператором |
| Адреса є, а тип доставки `null` | qwen-30b, llama | зайве уточнення |
| Страву, якої немає в меню, підмінено схожою («каліфорнія з крабом» → філадельфія з сурімі) | llama (**в items, без оператора**), qwen-30b (ambiguous) | у llama — небезпечна помилка |
| Склеювання кількох страв в одну згадку, пропущені позиції, сміття в `not_found` | переважно llama | слабка модель не тримає структуру |
| `"тот же"` як адреса / `delivery` за «адрес тот же» | Gemini | безпечно: позицій немає, уточнення все одно |

Висновок: у сильних моделей помилки переважно **безпечні** — вони збільшують кількість уточнень, а не пропускають неправильне замовлення.

## Обмеження

- **Dev set малий (20 прикладів)** і використовувався під час розробки: правила в prompt формулювалися, дивлячись на його помилки. Тому цифри на dev set оптимістичні; прихований набір покаже реальну узагальнюваність.
- **Гарантія коду — «немає вигаданих SKU», а не «немає неправильних SKU».** Якщо модель упевнено вибере існуючу, але не ту страву, фільтр цього не зловить.
- **Токени при повторах рахуються лише для останньої спроби** (`create_with_completion`). Невдалі спроби теж коштують грошей.
- **Сервіс stateless**: «повторіть минуле замовлення» неможливо виконати, такий запит іде на уточнення.
- **`now` не використовується для перевірки «час уже минув»** — у ТЗ явно вимагається лише графік.
- **Опції**: парсер меню розрахований на одну опцію на позицію (як у поточному меню).
- **Стоп-лист**: передбачається атомарний запис файлу (temp + rename); частково записаний файл під час читання призведе до помилки запиту.

## Що покращив би за тиждень

- **Більший eval set** з реальних повідомлень + holdout, на якому не тюниться prompt. Окремий набір на prompt injection і краєві випадки.
- **Правило «є адреса → доставка» перенести в код**, а не просити модель: eval показав, що моделі нестабільно його застосовують.
- **Уточнення prompt за результатами eval:** адреса в базовій формі без прийменників; кілька кандидатів — лише якщо кожен підходить під усі деталі; страва, якої немає в меню, не підміняється схожою.
- **`enum` для значень опцій у схемі LLM**, згенерований із меню: модель фізично не зможе повернути неіснуючий варіант.
- **Точний облік токенів і вартості з урахуванням повторів** через hooks instructor.
- **Перевірка дати стоп-листа** (попередження, якщо файл учорашній).
- **Використати `now`**: уточнення, якщо час доставки вже минув або клієнт пише «якнайшвидше», коли ресторан закритий; розбір відносного часу («через годину»).
- **Unit-тести `rules.py`** на всі краєві випадки + тест на «ідеальних» відповідях.
**CI/CD**
- На кожен push: `ruff check`, `ruff format --check`, unit-тести `rules.py` — швидко, без мережі й LLM.
- На PR, що змінює prompt, схему LLM або модель: прогін `eval.py` на dev set як quality gate. Деплой блокується, якщо є вигадані SKU, небезпечні авто-підтвердження або Items F1 впав нижче порогу.
- Після merge у `main`: збірка Docker-образу з тегом коміту, push у registry, деплой на сервер (наприклад, GitHub Actions → registry → `docker compose pull && up -d`), перевірка `GET /health` після викатки і відкат на попередній образ, якщо health не проходить.

## Як запустити в продакшн

**Що вже є в репозиторії:** fallback на оператора (порожнє замовлення з `needs_clarification=true`, заголовок `X-LLM-Fallback: true`, traceback у лог) і `GET /health` для healthcheck.

Решта нижче — план, що я зробив би перед продакшном. У поточному коді цього немає.

**Надійність**
- Резервна модель у LiteLLM (fallbacks): при 429/5xx запит іде на іншу модель без змін у сервісі.
- Transport retries з backoff в OpenAI SDK (429, 5xx, таймаути) — окремо від validation retries в instructor.
- Кілька workers / реплік за балансувальником, `GET /health` для readiness.

**Логування**
- Структуровані JSON-логи з `request_id`: модель, latency, токени, кількість повторів, fallback.
- Сирий `LLMOutput` поруч із фінальною відповіддю — щоб при розборі розрізняти помилки моделі та помилки правил.
- Логування відкинутих галюцинацій: вигадані SKU та неіснуючі опції, які відфільтрував `rules.py`.
- Обережно з персональними даними (адреси, телефони): маскування або обмежений retention.

**Моніторинг та алерти**
- Частка fallback-відповідей, p50/p95 latency, вартість на замовлення.
- Частка `needs_clarification` — різкий ріст означає деградацію моделі, проблеми з меню або новий тип повідомлень.
- Частка відкинутих галюцинацій.

**Якість у часі**
- Рішення операторів (що вони виправили після уточнення) — готові розмічені приклади для поповнення eval set.
- Регулярний прогін eval при зміні моделі, prompt або меню: регресія ловиться до релізу.
- Меню і стоп-лист — з облікової системи ресторану через API з коротким кешем, а не з файлів.
