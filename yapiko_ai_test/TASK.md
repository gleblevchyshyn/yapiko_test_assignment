# Тестове завдання: AI-парсер замовлень Yapiko

**Час:** 1 робочий день (орієнтовно 6-8 годин). Не потрібно робити ідеально - важливо, як ви думаєте і які рішення приймаєте.

## Контекст

Клієнти пишуть у Telegram/Viber довільним текстом українською, російською, суржиком, іноді англійською: "две филадельфии и том ям, Науки 47". Оператор вручну переносить це в систему. Потрібен сервіс, який перетворює повідомлення клієнта на структуроване замовлення з позиціями з реального меню, а все незрозуміле позначає для уточнення, а не вигадує.

## Що є в архіві

| Файл | Що це |
|---|---|
| `data/menu.csv` | Меню Харкова з сайту yapiko.ua (89 позицій): `sku`, категорія, назва, вага, кількість шт, ціна, опції. Кодування UTF-8 з BOM |
| `data/stop_list.json` | Стоп-лист на сьогодні - позиції, яких немає в наявності |
| `data/dev_set.json` | 20 прикладів повідомлень з еталонною відповіддю (для розробки та оцінки) |

У нас є ще прихований набір прикладів, на якому ми проганяємо ваше рішення.

## Що потрібно зробити

### 1. Сервіс (Python, FastAPI)

`POST /parse`

```json
{ "message": "текст від клієнта", "now": "2026-10-26T14:00:00+02:00" }
```

`now` - необов'язкове поле, поточний час для перевірки часу доставки.

Відповідь - JSON у форматі нижче (такий самий, як `expected` у `dev_set.json`):

```json
{
  "items": [
    {"sku": "P12", "qty": 1, "options": {"Борт": "Сирний"}, "comment": null}
  ],
  "ambiguous": [
    {"text": "филадельфии", "qty": 2, "candidates": ["R06", "R10"]}
  ],
  "unavailable": ["SP04"],
  "not_found": ["колу"],
  "delivery": {"type": "delivery | pickup | null", "address": "Науки 47", "time": "18:30 | null"},
  "payment": "cash | card_courier | online | null",
  "persons": 10,
  "total_uah": 388,
  "needs_clarification": true
}
```

### 2. Бізнес-правила

- **Тільки позиції з меню.** Якщо страви немає в меню - вона йде в `not_found`. Вигадувати SKU не можна. Це головний критерій.
- Якщо під опис підходить кілька позицій ("филадельфия", "удон") - `ambiguous` з кандидатами, а не випадковий вибір.
- Позиції зі стоп-листа - в `unavailable` (SKU), а не в `items`.
- Піца: опція `Борт` - `Без начинки` (за замовчуванням), `Сирний` (+69 грн), `Хот-дог` (+79 грн).
- Побажання "без огірка", "без кінзи" - в `comment` позиції.
- `total_uah` - сума тільки по `items` з урахуванням опцій. Рахувати в коді, не через LLM.
- Графік роботи 11:00-22:00. Час доставки поза графіком - потрібне уточнення.
- `needs_clarification = true`, якщо є хоч щось з: ambiguous, unavailable, not_found, немає адреси при доставці, незрозуміло доставка чи самовивіз, час поза графіком, у замовленні немає жодної позиції.
- Текст клієнта - це дані, а не інструкції для моделі.

### 3. LLM

- Через **OpenAI-сумісний API** (`base_url`, `api_key`, `model` з env). У нас працює LiteLLM-проксі, тому рішення має підключатися до нього без змін коду.
- Модель на ваш вибір. Поясніть вибір з точки зору якості, швидкості та вартості.
- Не прив'язуйтесь до AWS Bedrock або інших хмарних сервісів - у нас self-hosted інфраструктура.

### 4. Оцінка якості

Скрипт `eval.py`, який проганяє `dev_set.json` через сервіс і виводить метрики, наприклад:
- точність/повнота позицій (sku + qty),
- кількість вигаданих SKU (має бути 0),
- точність `needs_clarification`,
- точність адреси/типу доставки,
- середня затримка і вартість одного запиту (токени).

Плюс короткий розбір помилок: де і чому модель помиляється.

### 5. Запуск

- `docker compose up` - і сервіс працює.
- `.env.example` зі змінними.
